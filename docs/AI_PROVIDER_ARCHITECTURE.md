# AI_PROVIDER_ARCHITECTURE — NEUROOS APP FACTORY

Версия: 0.1.0 · Статус: PROPOSED → на утверждение (GATE 1)

## 1. Принцип

Система не привязана к одному ИИ-провайдеру. Все вызовы ИИ идут через **AI Provider Layer**
(`packages/ai-provider-layer`) — единственную точку входа модулей конвейера к моделям.
Замена провайдера — конфигурация, а не переписывание бизнес-логики.

Текущая исполнительская среда разработки (агент) — рабочий инструмент этапа, но в
архитектуру приложения не встраивается.

## 2. Контракт провайдера

```ts
interface AIProvider {
  readonly id: string;
  readonly models: ModelInfo[];            // capabilities, context, limits

  complete(req: {
    model: string;                          // конкретная модель провайдера
    taskKind: TaskKind;                     // spec_generate | arch_generate | code_task |
                                            // ui_generate | test_generate | audit_review | ...
    messages: Message[];                    // системный + пользовательский контекст
    schema?: JSONSchema;                    // структурированный вывод, если применимо
    timeoutMs: number;
    idempotencyKey: string;
  }): Promise<AIResult>;                    // ok | error | rate_limited | timeout
}
```

Гарантии контракта:
- `AIResult` содержит фактический ответ или фактическую ошибку — имитация ответа запрещена.
- Каждый вызов пишется в `ai_task_run` (промпт и ответ — в S3, метаданные — в БД).
- Повтор возможен только с тем же `idempotencyKey` (защита от дублирования операций).

## 3. Реестр и маршрутизация

- **Реестр провайдеров** (`ai_provider`): имя, base_url, модели, лимиты, enabled, `key_ref`.
- **Маршрутизация задач:** каждому `taskKind` сопоставляется приоритетный список
  `(provider, model)` в конфигурации; при недоступности/лимите — следующий в списке;
  при исчерпании — задание уходит в очередь повторов (pg-boss) или в ручной режим.
- **Назначение модели на задачу** настраивается владельцем в AI Workspace.

## 4. Управление ключами

- Ключи хранятся только в хранилище секретов (файлы, монтируемые средой, или секрет-менеджер);
  в БД — только ссылка `key_ref`. В коде, репозитории, логах и артефактах ключей нет.
- Ключ никогда не попадает в `ai_task_run.prompt_ref/response_ref` (фильтрация при записи).
- Ротация ключа — операция владельца; аудит всех использований — в `audit_log`.

## 5. История и наблюдаемость

- `ai_task_run`: провайдер, модель, тип задачи, ссылки на промпт/ответ, токены, статус,
  ошибка, время. История видна в AI Workspace.
- Лимиты и ошибки: backoff для rate_limited, отдельный статус для timeout, понятные
  сообщения пользователю без раскрытия ключей.

## 6. Ограничения (честно)

- Конкретные провайдеры и их API на STAGE 0 не проверялись: доступов и технической
  проверки документации нет. Подключение каждого провайдера на этапе реализации
  сопровождается проверочным вызовом (smoke-test) до появления в реестре как enabled
  («Промпт 1» §4: не заявлять об API без проверки).
- Поведение моделей недетерминировано: все ИИ-результаты проходят валидацию схемы и
  попадают в Gate-процедуры; автоматическое утверждение критических этапов по ответу ИИ
  запрещено.
