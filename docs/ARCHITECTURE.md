# ARCHITECTURE — NEUROOS APP FACTORY

Версия: 0.1.0 · Статус: PROPOSED → на утверждение (GATE 1)

## 1. Метод выбора стека

«Промпт 1» §10 требует анализа совместимости до утверждения стека. Оценка велась по
критериям: (а) покрытие платформ Web/PWA/Desktop/Mobile; (б) совместимость с NeuroOS Core
(React + Vite, Tauri 2 — ADR-F-002/003); (в) offline-first; (г) управляемость конвейера;
(д) зрелость экосистемы для сборки EXE/DMG/AppImage/APK.

### 1.1. Анализ вариантов

| Технология | Роль-кандидат | Оценка | Решение |
|---|---|---|---|
| TypeScript | язык всего проекта | строгая типизация, общий код UI/логики/сервера | **ПРИНЯТ** |
| React + Vite | UI фабрики | фиксируется архитектурой NeuroOS Core (ADR-F-002/003); исключает дублирование соглашений | **ПРИНЯТ** |
| Next.js | альтернатива Vite | даёт SSR, но фабрика — приложение-инструмент, SSR не нужен; усложняет Tauri-обёртку | отклонён |
| Electron | desktop-обёртка | тяжелее (Chromium в комплекте), слабее изоляция | отклонён |
| Tauri 2 | desktop + mobile-обёртки | один shell → Windows/macOS/Linux + Android/iOS; малый вес; системный webview; совпадает с Core | **ПРИНЯТ** |
| React Native / Expo | альтернатива mobile | вторая UI-кодовая база; нужен только если Tauri mobile не закроет требования проекта | резерв (на проект) |
| Fastify | backend API | производительный, schema-first (JSON Schema), зрелый | **ПРИНЯТ** |
| PostgreSQL | серверная БД | надёжность, JSONB, транзакции для реестра и очередей | **ПРИНЯТ** |
| SQLite | локальная БД (desktop-режим офлайн у фабрики и у произведённых продуктов) | встроенная, без сервера | **ПРИНЯТ** |
| IndexedDB | браузерное хранение (web-режим) | стандарт PWA | **ПРИНЯТ** |
| pg-boss | очередь задач на PostgreSQL | job-конвейер (сборки, тесты, ИИ-задачи) без новой инфраструктуры | **ПРИНЯТ** |
| S3-compatible storage | хранилище артефактов | MinIO/S3 API; чек-суммы, версионирование | **ПРИНЯТ** |
| Git + GitHub Actions | исходники и CI/CD | стандарт; контроль зависимостей и проверок | **ПРИНЯТ** |
| WebSocket | реального времени | статусы задач конвейера, логи сборок | **ПРИНЯТ** (канал статусов) |

### 1.2. Итоговый стек

- **UI:** React 18 + Vite + TypeScript (единая дизайн-система NeuroOS).
- **Desktop/Mobile shell:** Tauri 2 (Windows, macOS, Linux, Android, iOS).
- **Backend:** Fastify (TypeScript) + REST + WebSocket; PostgreSQL; pg-boss.
- **Локальный слой:** SQLite (desktop), IndexedDB + Service Worker (web/PWA).
- **Артефакты:** S3-compatible (MinIO в dev), контрольные суммы SHA-256.
- **Процессы:** Git, GitHub Actions, автоматизированные проверки качества и безопасности.

### 2.1. Ключевые узлы

- **Pipeline Engine (pg-boss):** каждая операция конвейера (генерация ТЗ, прогон тестов,
  сборка, релиз) — job с входом, выходом, журналом и статусом. Идемпотентность и повтор
  при ошибке; очередь отложенных offline-операций.
- **Runner:** изолированное выполнение команд (git, pnpm, tauri build, тесты) в рабочем
  каталоге проекта с ограничениями (SECURITY_MODEL.md §4). Никаких «виртуальных»
  выполнений — только фактические процессы и их реальные коды возврата.
- **Gate Service:** проверка критериев Gate по артефактам; переход жизненного цикла
  возможен только через утверждённый Gate (PROJECT_LIFECYCLE.md §3).
- **AI Provider Layer:** единый интерфейс `generate(task) → artifact`; маршрутизация задач
  на провайдеров; ключи только в хранилище секретов (AI_PROVIDER_ARCHITECTURE.md).

## 3. Границы модулей

См. MODULES.md. Каждый модуль — пакет монорепозитория со своим публичным API; модули
общаются через контракты (TypeScript-типы + REST/jobs), не через прямые импорты внутренностей.

## 4. Offline + Online (для самой фабрики и для произведённых продуктов)

- **Offline:** локальная БД (SQLite/IndexedDB), очередь отложенных операций, локальные
  настройки, восстановление после перезапуска, защита от потери данных.
- **Online:** синхронизация, авторизация, резервное копирование, серверные функции.
- **Синхронизация:** определение состояния подключения, очередь локальных изменений,
  повторная отправка при ошибках, разрешение конфликтов (last-writer-wins по умолчанию +
  вектор версий для критичных сущностей), защита от дублирования операций (idempotency key),
  контроль целостности (чек-суммы). Честная индикация функций, требующих интернет.

## 6. Архитектурные решения (ADR-заготовки)

- **ADR-AF-001:** монорепозиторий pnpm-workspace; причина — общие контракты и атомарные
  версии пакетов фабрики.
- **ADR-AF-002:** Tauri 2 вместо Electron; причина — совпадение с NeuroOS Core, вес,
  мобильные цели из одного shell.
- **ADR-AF-003:** очередь задач на PostgreSQL (pg-boss), а не Redis/RabbitMQ; причина —
  одна инфраструктура, транзакционная гарантия job + состояние.
- **ADR-AF-004:** артефакты — только в S3-хранилище с SHA-256; файловая система Runner —
  временное рабочее пространство.
- **ADR-AF-005:** React Native/Expo — не в базовом стеке; применяется в произведённом
  продукте, если его архитектура этого требует (стандарт §3 допускает выбор стека продукта).

## 7. Риски архитектуры

| Риск | Влияние | Митигация |
|---|---|---|
| Tauri mobile (Android/iOS) моложе конкурентов | сроки STAGE 5 | прототип сборки на STAGE 1; резерв — Expo для мобильного клиента продукта |
| Сборка под Windows/macOS требует целевых ОС | BLOCKED-статусы сборок | CI-матрица на GitHub Actions (windows-latest, macos-latest) |
| Зависимость от одного ИИ-провайдера | простой конвейера | мультипровайдерность, очереди повторов, деградация в ручной режим |
| Сложность синхронизации конфликтов | потеря данных | idempotency-ключи, векторы версий, обязательные тесты STAGE 4 |
