# Руководство пользователя — NeuroOS App Factory

Версия API: 0.7.0 (аутентификация и роли). Документ описывает работу с интерфейсом
фабрики и API с точки зрения пользователя.

## 1. Навигация по интерфейсу

| Раздел | Назначение |
|---|---|
| **Global Dashboard** | сводка фабрики: количество проектов, заданий, релизов; живые события по WebSocket |
| **Projects** | список всех проектов с их статусами жизненного цикла |
| **Project Workspace** | карточка проекта: смена статусов, задания, артефакты, панель ворот G0–G6 |
| **AI Workspace** | настройка AI-провайдеров (ключи только как key_ref, smoke-test) |
| **Build Center** | сборки и установщики, артефакты с SHA-256 |
| **Audit Center** | отчёты аудита, SAST/сканер секретов |
| **Release Center** | RELEASE HUB: реестр релизов, создание релиза, проверка обновлений |
| **Settings** | настройки фабрики |

## 2. Типовой производственный сценарий

1. **Создать проект** — Projects → создать (статус IDEA).
2. **Заполнить критерии приёмки** — PATCH проекта: список `acceptanceCriteria`
   (создание игнорирует это поле; критерии задаются отдельным изменением).
3. **Зарегистрировать артефакты** — загрузка с SHA-256; при расхождении хэша — 409,
   артефакт не принимается.
4. **Запустить задания** — конвейер `code_task → build_run → test_run`; честные
   ошибки (нет AI-ключа, команда вне whitelist) видны в статусе задания.
5. **Пройти ворота G0–G6** — панель ворот показывает, чего не хватает
   (`artifact:spec`, `check:acceptance_criteria_defined`); approve доступен
   соответствующей роли: G0/G6 — только owner.
6. **Создать релиз** — Release Center: канал по правилам
   (stable ← G5+G6, beta ← G5, alpha/dev свободно); нарушение — 409 со списком
   недостающего.
7. **Проверить обновления** — панель проверки обновлений сравнивает версии
   численно (0.10.0 > 0.2.0) и честно отвечает «обновлений нет» при 404.

## 3. Офлайн-работа (веб-интерфейс)

- При недоступности сети GET-данные отдаются из кэша localStorage с честным
  маркером «из кэша» (data-testid `offline-cache`).
- Мутации при сетевом сбое попадают в офлайн-очередь; счётчик ожидающих операций
  виден в шапке (chip с числом).
- Автоматическая отправка очереди при восстановлении WS-соединения или событии
  `online` браузера. Ошибки `ApiError` (логические отказы сервера) в очередь не
  попадают — только сетевые сбои.
- Конфликты решаются по LWW (last-write-wins) с ревизиями проекта.

## 4. Аутентификация и роли (API v0.7.0)

Токены задаются переменной среды `NF_AUTH_TOKENS` в формате `token:role` через
запятую:

```bash
export NF_AUTH_TOKENS="владельческий-токен:owner,инженерный-токен:engineer,токен-наблюдателя:viewer"
```

Клиент передаёт токен в заголовке: `Authorization: Bearer <token>`.

| Роль | Права |
|---|---|
| **owner** | всё: утверждение/отклонение ворот, релизы, настройки, рабочие операции |
| **engineer** | рабочие операции: проекты, задания, sync (GET + мутации); ворота approve/reject, релизы, настройки — 403 |
| **viewer** | только GET; любые мутации — 403 |

- Если `NF_AUTH_TOKENS` не задан — режим открыт (без аутентификации); `/healthz`
  честно сообщает `auth: "disabled"`.
- `/healthz` и пути вне `/api/v1/` открыты всегда; при включённой аутентификации
  все `/api/v1/*` требуют валидный токен (иначе 401), а WebSocket `/ws` — токен
  в запросе (`/ws?token=...`).
- В веб-интерфейсе токен задаётся в **Settings → «Доступ (токен API)»**: он
  сохраняется в localStorage браузера и автоматически отправляется во все
  запросы API, офлайн-очередь и WebSocket.
- Некорректные пары в `NF_AUTH_TOKENS` игнорируются при разборе.

## 5. Программный доступ к API (OpenAPI)

Сервер публикует собственный машинночитаемый контракт:

- **`GET /api/v1/openapi.json`** — OpenAPI 3.1, 20 путей, securityScheme `bearerAuth`.
  Эндпоинт открыт всегда (как `/healthz`), токен не требуется. Если файл спеки
  не найден на диске — честный 503.
- В веб-интерфейсе спека скачивается в **Settings → «API-контракт (OpenAPI)»**.

Примеры обращения к API:

```bash
# состояние сервиса (открыто всегда)
curl http://127.0.0.1:3000/healthz

# спека API (открыто всегда)
curl http://127.0.0.1:3000/api/v1/openapi.json -o openapi.json

# список проектов (при включённой аутентификации — с токеном)
curl -H "Authorization: Bearer инженерный-токен" http://127.0.0.1:3000/api/v1/projects

# создание проекта (engineer или owner)
curl -X POST -H "Authorization: Bearer инженерный-токен" \
  -H "content-type: application/json" \
  -d '{"name":"Моё приложение","slug":"my-app"}' \
  http://127.0.0.1:3000/api/v1/projects
```

Спека описывает коды ошибок для каждого маршрута (401/403/409/413) и ограничения
ролей — используйте её как источник истины при написании интеграций.

## 6. Частые ошибки и их смысл

| Ситуация | Причина |
|---|---|
| 409 при загрузке артефакта | SHA-256 в запросе не совпадает с SHA-256 содержимого |
| 409 при смене статуса на RELEASED | нет утверждённого G6 или не все критерии приёмки DONE |
| 409 при создании релиза | правила каналов: stable требует G5+G6, beta — G5 (в ответе список недостающего) |
| 409 duplicate | релиз с такой версией и каналом уже существует |
| GateApprovalError | ворота нельзя утвердить: не хватает артефактов/проверок/предшествующих ворот |
| 403 «viewer role is read-only» | viewer пытается выполнить мутацию |
| 403 «gate decisions require owner role» | engineer пытается утвердить/отклонить ворота |
| 403 «this operation requires owner role» | engineer пытается создать релиз или изменить настройки |
| 401 | нет токена или токен неизвестен |
| Маркер «из кэша» в интерфейсе | данные отданы из офлайн-кэша, сеть недоступна |
| Счётчик в шапке | число операций в офлайн-очереди, ожидающих отправки |
