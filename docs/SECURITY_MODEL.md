# SECURITY_MODEL — NEUROOS APP FACTORY

Версия: 0.1.0 · Статус: PROPOSED → на утверждение (GATE 1)

## 1. Изоляция проектов

- Каждому проекту — собственный рабочий каталог Runner и собственный git-репозиторий.
- Проекты не имеют доступа к файлам и БД друг друга; доступ Runner ограничен каталогом
  проекта (рабочее пространство), таймаутами и белым списком команд.
- Сетевой доступ Runner ограничивается задачей (менеджеры пакетов, целевые сервисы сборки).

## 2. Безопасное выполнение команд

- Белый список исполняемых программ (git, pnpm/npm, node, cargo/tauri, тест-раннеры);
  произвольные shell-команды — запрещены по умолчанию.
- Журнал каждого выполнения: argv, cwd, exit code, stdout/stderr (с маскированием секретов).
- Отмена/таймаут — обязательные параметры job; зависший процесс завершается и фиксируется.

## 3. Контроль прав доступа

- Роли: **owner** (всё, утверждение Gates, релизы), **engineer** (рабочие операции),
  **viewer** (чтение). Матрица прав — в IMPLEMENTATION_ROADMAP (STAGE 1).
- Критические операции (утверждение Gate, релиз, удаление, изменение Git-истории,
  публикация) доступны только owner и требуют подтверждения (controlled execution).

## 4. Секреты

- Секреты (API-ключи, сертификаты, подписи) — только в хранилище секретов среды;
  в БД — ссылки (`key_ref`), в коде/репозитории/логах — никогда.
- Автоскан коммитов и логов на секреты — часть GATE 4.
- Утечка ключа — немедленная ротация + инцидент в audit_log.

## 5. Аудит действий

- `audit_log` (append-only): кто, что, когда, с каким объектом и результатом.
- Аудируются: входы, изменения проектов, переходы жизненного цикла, утверждения Gates,
  вызовы ИИ, сборки, релизы, операции с секретами, изменения прав.

## 6. Защита репозиториев и Git-истории

- Изменение существующей Git-истории (force-push, rebase опубликованных веток) — только
  с явного разрешения владельца («Промпт 1» §11).
- Защищённые ветки (main/master) — только через PR с проверками CI.
- Подпись коммитов (signed commits) — целевой режим STAGE 1+.

## 7. Контроль зависимостей

- Фиксация версий (lock-файлы), автоматические проверки уязвимостей (npm/pnpm audit,
  cargo audit) в CI, обновления — контролируемые, с прогоном тестов.
- Сгенерированный код проходит те же проверки, что и ручной; непроверенный сгенерированный
  код не попадает в защищённые ветки.

## 8. Защита от небезопасного сгенерированного кода и ИИ-агентов

- Лимит доступа ИИ-агентов к файловой системе: только рабочее пространство проекта,
  только через RUNNER с белым списком.
- Все ИИ-результаты — через валидацию схемы и ревью конвейера; автоматическое утверждение
  критических этапов по ответу ИИ запрещено.
- Статический анализ (SAST) и сканер секретов — обязательные шаги CI.

## 9. Защита данных, резервное копирование, восстановление

- Шифрование чувствительных данных: TLS в транспорте, шифрование диска/бэкапов хранилища.
- Резервное копирование PostgreSQL и S3 по расписанию; проверка восстановления —
  обязательная процедура (восстановление без проверки не считается выполненным).
- Произведённые продукты наследуют требования стандарта §7: безопасное хранение,
  защита сессий, шифрование чувствительной информации, бэкапы.

## 10. API и веб-безопасность

- Валидация всех входных данных (schema-first на Fastify), авторизация на каждом эндпоинте.
- Защита от распространённых веб-уязвимостей (OWASP Top 10): инъекции, XSS, CSRF,
  небезопасная десериализация, некорректная конфигурация.
- CORS/заголовки безопасности, ограничение частоты запросов, безопасные сессии
  (HttpOnly, SameSite, срок жизни).
